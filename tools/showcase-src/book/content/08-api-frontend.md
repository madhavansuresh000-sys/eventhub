# 8. REST API reference

## 8.1 What a REST API is

The backend offers its features as **URLs** that the frontend (or Postman, or a test) calls with an HTTP **method**:

| Method | Meaning | Example |
|---|---|---|
| GET | read, changes nothing | `GET /api/events/2` - one event |
| POST | create or trigger an action | `POST /api/bookings` - hold seats |
| PUT | replace / set to this value | `PUT /api/events/2` - save the edited event |
| DELETE | remove | (not needed in EventHub; things are cancelled, not deleted) |

Answers use HTTP **status codes**: 200 OK, 201 Created (with a `Location` header), 204 No Content, 400 Bad Request, 401 Unauthorized (not logged in), 403 Forbidden (not allowed), 404 Not Found, 409 Conflict (a business rule said no), 429 Too Many Requests, 500 Server Error.

>> A REST API is like the menu of a restaurant: every dish (URL) has a name and a way to order it (method). You do not walk into the kitchen; you order from the menu and the waiter brings the answer.

## 8.4 Swagger UI

The full, always-current API description is generated by springdoc-openapi from the controllers. Log in as the admin in the React app, then open http://localhost:8080/swagger-ui.html. Each endpoint can be tried directly from the page ("Try it out"). It is admin-only because a complete map of the API is valuable information for an attacker.

## 8.5 The Postman collection

`postman/EventHub.postman_collection.json` contains 25 requests in folders (catalogue, create and edit, approval workflow, error cases) with 43 automatic checks such as "status is 201" and "the Location header points to the new event". It is a quick way to see that the API works after a change.

## 9.3 Talking to the backend

@lines frontend/src/api/client.js :: 1 :: 12

All calls go through this one Axios instance. The base address `/api` goes to the Vite dev server, which forwards it to Spring Boot. Axios automatically sends cookies (the login) and copies the `XSRF-TOKEN` cookie into the `X-XSRF-TOKEN` header, which is exactly what the backend's CSRF protection expects.

When a call fails, `describeError` turns the backend's Problem Details into `{ status, message, fieldErrors }` that every page can show:

@code frontend/src/hooks/useAsync.js :: export function describeError

The store also installs an **interceptor**: if any call answers 401 while the app thinks someone is logged in, the login has expired (after 8 hours) - the app forgets the user and says "Your login has expired".

## 9.4 Redux slices

| Slice | Holds | Main actions |
|---|---|---|
| auth | the logged-in user, loading status | `loadSession`, `login`, `register`, `logout`, `sessionExpired` |
| cart | the seats being held and when the hold ends | `seatsHeld`, `cartCleared` |

| admin | approval queue, club stats, audit log | `approveEvent`, `rejectEvent`, `loadClubStats` |

An **async thunk** is an action that calls the API and has three outcomes: pending, fulfilled or rejected. Example:

@code frontend/src/store/organizerSlice.js :: export const loadClubEvents

>> A thunk is like sending a friend to the shop: you note "gone to the shop" (pending), then either "came back with milk" (fulfilled) or "shop was closed" (rejected). The page shows a spinner, the data, or an error for each case.

## 9.5 Protecting pages: RequireAuth

@code frontend/src/components/auth/RequireAuth.jsx :: export default function RequireAuth

Used in `App.jsx` around groups of routes, e.g. `<Route element={<RequireAuth allow={isAdmin} what="the admin area" />}>`. As the comment in the code says: this only **hides** pages. The backend checks every request again.

## 9.6 Forms and validation

`useForm` keeps the values of a form, validates them with small rules from `utils/validation.js`, shows an error only after the user leaves a field (or presses submit), puts the cursor on the first wrong field, and can show errors that came back from the server.

@code frontend/src/hooks/useForm.js :: export default function useForm

Example rules for the register form: email must look like an email, password at least 8 characters with letters and numbers (and at most 72 - BCrypt only reads 72 bytes), "confirm password" must match, and the rules checkbox must be ticked. The backend checks the same rules again with Bean Validation, because anybody can call the API without the React app.

## 9.7 Timers, QR codes, charts and code splitting

- **Seat-hold timer** - `useCountdown(endsAt)` recalculates from the real clock every second, so it stays right even if the phone put the tab to sleep. The end time comes from the server (`secondsLeft`).

@code frontend/src/hooks/useCountdown.js :: export default function useCountdown

- **QR camera** - `QrCamera` uses html5-qrcode to read the code from the camera; on devices without a camera the volunteer types the code.
- **Charts** - `AnalyticsDashboard` draws two bar charts with Recharts (tickets per day, money per day - never on one axis, because they have different scales), plus a table view for screen readers.
- **Code splitting** - organizer, admin, scanner and analytics pages are loaded with `React.lazy`. The first download fell from 1,213 kB to 329 kB; the chart and camera libraries load only when those pages open.

## 9.8 Design system, dark mode and accessibility

- Colours are **design tokens** in `index.css` (`--color-brand-50` … `--color-brand-900`, indigo), used as Tailwind classes such as `bg-brand-600`.
- Dark mode: a `dark` class on `<html>`; `useTheme` remembers the choice in localStorage; the first visit follows the device setting.
- Every input has a `<label>`; errors are linked with `aria-describedby`; scan results use `role="alert"` so screen readers announce them.
- Phase 8 measured every public page at 375 px (phone) in light and dark mode: no sideways scrolling, tap targets at least 24 px, and text contrast at least 4.5:1. Sixty-two grey hint texts, the dark-mode buttons and the green "Let in" panel were darkened or lightened to pass.

# 10. User guide (with screenshots)

This chapter shows how each kind of user works with EventHub. The screenshots come from the real application (demo data, dark mode).

## 10.1 Visitor: finding events

1. Open the home page. Type in the search box or click a tag chip such as **robotics**.
2. The events page shows matching events. Use the filters on the left: tag, club, dates, sort order. The address bar keeps the filters, so the link can be shared.

![All events filtered by the tag "robotics"](02-events-filter.png)

3. Click an event to see its details and the live seat bar. Pressing **Book now** without being logged in opens the login page, which brings you back to the event afterwards.

![Login page - after login EventHub returns to the event you were looking at](04-login.png)

## 10.2 Student: booking and paying

1. On the event page, choose the number of tickets (1-10) and press **Book now**.

![Event details: price, live "booked / total" bar, ticket stepper](05-event-details.png)

2. The checkout page shows your details and a **10-minute timer**. The seats are yours while it runs. Press **Pay**. (Press "Release my seats" if you changed your mind.)

![Checkout: seats held, total, Pay button](07-checkout-hold.png)

3. In development you see EventHub's **test payment page** (no real money). With a Stripe test key you would see Stripe's own page instead. Press **Pay**.

![The built-in test payment page](08-test-payment.png)

4. "Payment received. You are going!" Press **Show my ticket**.

![Booking confirmed with the QR code](10-booking-confirmed.png)

5. The ticket page shows the QR code and the ticket code. Print it or save it as PDF - or just show it on the phone at the gate.

![The QR ticket](11-qr-ticket.png)

## 10.3 Student: my tickets, waitlist, notifications

- **My tickets** lists upcoming, past and cancelled bookings. A paid ticket can be cancelled before the event (the money is refunded); a ticket still waiting for payment shows "Pay now".

![My tickets](12-my-tickets.png)

- **Waitlist**: on a sold-out event press "Join the waitlist" and choose how many seats you need. The waitlist page shows your place ("You are #2"). When seats are offered, a card with a 30-minute countdown appears: press **Accept** to go to checkout.
- **Bell**: the bell in the top bar shows unread notifications (booking confirmed, seat offered, event approved, reminders). The same messages arrive by email (in development: the Mailpit inbox at http://localhost:8025).

## 10.4 Student: certificates and feedback

After an event you attended (your ticket was scanned at the gate) is over, it appears under **Certificates**.

![My certificates](13-certificates.png)

Open it to see the certificate and download the PDF. The QR code in the corner opens the public verify page.

![The certificate](14-certificate.png)

On **My tickets → Past**, press **Rate** to give 1-5 stars and an optional comment. You can change your rating later.

## 10.5 Volunteer: the gate scanner

1. Log in as a volunteer (for example Priya). Open **Scanner** in the top bar.
2. Choose the event you are on duty for. The live counter shows "checked in / booked" for all gates together.
3. Press **Scan with camera** and point it at the QR code - or type the code and press **Check**.

![First scan: LET IN, with the name and number of people](15-gate-let-in.png)

4. The answer is big and coloured: green **LET IN**, or red **ALREADY USED** / **STOP**. Phones vibrate on red.

![The same ticket again: ALREADY USED, with the time and the volunteer's name](16-gate-already-used.png)

## 10.6 Anyone: verifying a certificate

Open `/verify` (link "Verify a certificate" in the footer) and type the number, or scan the QR code on the certificate. No login is needed.

![A genuine certificate on the public verify page](17-verify-public.png)
